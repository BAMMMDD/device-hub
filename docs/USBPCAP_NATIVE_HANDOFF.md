## 2. 実装順と完了条件

### A. Rust 計測器を抽出する

推奨配置は `crates/devhub-polling`。既存の `capture / consume / Samples / Capture` とテストを移し、OBS 専用のログ呼び出しと表示文字列を境界の外へ出す。生の USB レポートを UI に流す必要はない。共通 API は対象、計測ハンドル、状態スナップショット、停止を扱う。Windows 固有処理は `cfg(windows)` の内側に置く。

- **対象**はハブ・現在の USB アドレス・IN エンドポイント・任意の Report ID。永続化する個体識別情報と、接続ごとに変わり得るアドレスを分ける。
- **状態**は停止、初回入力待ち、計測中、切断、ドライバ未導入、権限不足、ハブ使用中、その他の I/O エラー。受信前は「待機」、受信後に直近 1 秒が空なら「0 Hz」と表示する。エラーには OS コードを残す。この PC では通常権限のハブ列挙は成功し、計測用の読み書きオープンはエラー 5 だった。
- **数値**はキャプチャ時刻を使い、対象の成功した interrupt IN 完了、データあり、必要なら Report ID 一致だけを数える。USB レートはレシーバーから PC への転送数。無線区間の周期や静止中のバスポーリング試行はこの値に含まれない。
- **ピーク**は受信ごとに区間 `(t − 1 秒, t]` の件数を更新し、期間中の最大を保持する。表示更新 250 ms のタイミングだけで最大を取ると中間の山が落ちる。計測開始前の履歴を混ぜず、終了後に「最高 7,968 Hz（連続 1 秒）」のように単位と区間を残す。
- **終了処理**は静止中のブロッキング read を解除してから join する。現行の `Drop` は終了まで待つため、設定変更や解除で描画スレッドを長く占有しない構造にする。DLL アンロード前に全ワーカーが終了することも確認する。

**完了条件**　OBS の既存シーンをそのまま開ける。模擬 125 Hz・1 kHz・8 kHz、1 秒境界、別アドレス・別 Report ID・失敗転送・要求側パケット・短いレコード・途中 EOF を Rust のテストで識別できる。静止中の計測停止が完了する。[USBPcap レコード仕様](https://desowin.org/usbpcap/captureformat.html)・[ドライバ公開ヘッダー](https://github.com/desowin/usbpcap/blob/master/USBPcapDriver/include/USBPcap.h)

### B. GPUI の通常操作から使えるようにする

テスト画面に「計測方式」「開始／停止」「現在」「期間内の最高」を置く。USB バックエンドの起動・終了は UI スレッド外で処理し、既存の HID 設定書き込みワーカーをキャプチャ read で塞がない。性能画面も同じスナップショットを参照する。Raw Input のギャップ・移動量・DPI 診断はその方式に属する値として扱う。USB 計測で権限不足や未導入が起きたら理由と利用可能な方式を表示し、異なる経路の値にはそれぞれ計測元を明記する。

UI の表示可否は既存の caps と計測バックエンドの利用状態から決める。VID/PID 固有処理は列挙・ドライバ側に閉じる。契約 v2 の拡張が必要なら追加のみとし、デモも更新する。USB 計測が使えない状態でもキーボードテスト、デモ、通常のデバイス設定は利用できること。[プロジェクト規約](../AGENTS.md)・[性能画面](../crates/device-hub/src/pages/perf.rs)

**完了条件**　アプリだけを起動してテスト画面から計測し、別アプリを前面にしたままマウスを振れる。終了後に対象名・計測元・ピークが残る。途中で選択デバイスを変えても結果が別の個体に移らない。

### C. ハブ番号の手入力を製品選択に置き換える

Rust から Windows の USB ハブ・接続ポート・構成記述子を列挙し、OS のマウス HID コレクションとインターフェースを対応付ける。USBPcap ハンドルからハブへの対応は `IOCTL_USBPCAP_GET_HUB_SYMLINK` が出発点。製品名、シリアルまたはコンテナ ID、接続場所を候補に持ち、HID の移動用コレクションに対応する interrupt IN を選ぶ。複合 HID のベンダー通知やキーボード用エンドポイントは別扱いにする。

同型 2 台、共有エンドポイントに複数 Report ID、シリアルなし、ドングル単体などは自動決定が曖昧になり得る。候補の接続場所と短い「動かして確認」を出し、詳細設定から現在の手入力も使えるようにする。再接続時は保存した個体情報から再解決し、以前のアドレスを引き継いだ別機器を捕捉しない。

**完了条件**　アプリと OBS の双方で「LAMZU Orbital 8K Dongle」を選ぶだけで開始できる。抜き差し・ポート変更・同型 2 台で、対象を自動復帰できる場合と再選択が必要な場合を区別できる。

### D. アプリと OBS が同じハブを使う場合

現行コードは `.share_mode(0)` で開く。**共通クレートに移しても、別プロセスのハブ所有権は共有されない。** 初回リリースは明示的な排他でも有用。どちらかの計測中にもう片方を開くと「ハブ使用中」と表示し、先に始めた計測を維持する。OBS 内の複数シーンには既存ソースの参照を使える。

同時計測まで納品する場合は、ハブを開く Rust ヘルパーを 1 個にし、アプリと OBS が名前付きパイプ経由で対象を購読する構成を推奨する。最初の購読で開始、最後の解除で停止。配るのは対象識別子、状態、時刻付き集計値。クライアント別のピーク開始・リセットを分離する。管理者権限をヘルパーに限定するなら、パイプを同一ユーザーに制限し、UAC 取消・所有プロセス終了・再接続をテストする。OBS 単独起動でも利用できる配置にし、両配布物に同じプロトコル版を明記する。

**完了条件**　アプリ先行・OBS 先行の両方を試す。排他版では競合を正しく説明できる。同時購読版では片方を閉じても他方の値が更新され、最後に閉じるとハブを再取得できる。
